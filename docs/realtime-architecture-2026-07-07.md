# 实时快车道与后台扫描架构（2026-07-07）

## 问题

旧架构把全市场召回、精排、回测、盘口检查和交易串在同一轮中。2C2G VPS 的一轮耗时约 60–90 秒，Dashboard 与 Runner 还会并发读写完整 `binance_cache.json`。线上缓存曾达到约 35MB，并残留多个大型临时文件；遥测数据库约 1.7GB，主要来自每轮重复保存完整市场宇宙和候选明细。

## 新架构

系统拆分为两个计算通道，但共用唯一交易执行锁：

- `fast_lane`：每 2 秒读取本地 WebSocket 机会队列，一次处理最多 3 个币，目标预算 5 秒。
- `background_scan`：持续维护全市场召回、粗排、精排、质量和回测数据，不阻塞快车道。
- `critical execution`：两个通道在下单前进入同一执行锁，并重新拉取持仓；币种、方向或数量变化时废弃旧决策。

所有模式继续调用同一套 `build_best_growth_decision`、仓位、信用、质量、成本、换仓和风控逻辑。快车道只缩小输入币种范围，不降低最终准入标准。

## API预算

REST调用按上下文分级：

- 后台扫描最多使用本地预算的 70%。
- 普通请求最多使用 85%。
- 实时快车道和交易执行可使用预留预算。
- Binance真实 418/429 冷却仍具有最高优先级，所有通道都会等待恢复。

## 数据与缓存

- Binance缓存从整文件JSON改为SQLite WAL键值缓存。
- 单个缓存键独立更新，不再每次反序列化和重写几十MB文件。
- 最多保留约450–600个近期缓存键，并按时间清理。
- Runner原子写入 `runtime_snapshot.json`。
- Dashboard的市场、漏斗和耗时全部读取Runner快照，不再因页面刷新触发市场扫描。

## 遥测治理

- `bitdata.db`启用WAL、`NORMAL`同步和15秒busy timeout。
- 为权益、事件、币种策略记录和动作增加索引。
- 新策略记录移除600币完整列表、粗排大对象和无关回测字段，但保留胜率、PF、净收益、风险、信用、质量及交易结果。
- Dashboard日志接口默认不加载历史大payload。
- 每日清理过期系统事件和权益明细；成交与实盘学习记录不删除。

## 安全边界

- 已挂在Binance的止盈止损不依赖扫描线程。
- 快车道与后台扫描不能并发成交同一旧账户快照。
- 配置、状态和运行快照均使用临时文件原子替换。
- 快车道连续事件按币种默认合并10秒。
- 后台任务触达70%预算时只延后后台任务，不暂停机器人。
- 部署期间保留当前持仓及原保护参数。

## Dashboard

机会漏斗新增：

- 实时快车道耗时与处理币种。
- 后台全量扫描耗时。
- WebSocket、事件队列和行情状态。

新增中文配置：快车道开关、轮询、同币冷却、事件有效期、单次币数、计算预算和遥测保留周期。

## 验收目标

- 快车道P95决策耗时不超过5秒；若外部REST响应较慢，必须明确记录超时和降级。
- Dashboard刷新不增加全市场行情请求。
- 后台扫描不耗尽交易请求预算。
- 无重复下单、无裸仓、无持仓变化后执行旧决策。
- 数据库新增记录体积显著低于旧版本，缓存不再产生大型JSON临时文件。
- 现有2C2G稳定运行后再评估4C4G，不以增加内存替代架构治理。

## 本地基准与测试

- SQLite WAL缓存写入400个、每个含600根K线的键约 `2.88秒`，读取400个约 `0.94秒`；单键更新不再复制完整缓存文件。
- 构造的旧式扫描决策体积约 `823KB`，紧凑留档约 `3KB`，缩减约 `99.64%`，同时保留交易学习指标。
- 自动化测试覆盖缓存、API预算预留、原子快照、遥测索引、紧凑日志和快车道显式币种范围。
