# v0.16.1 / V4.6.1 两阶段聪明钱排序

## 背景

V4.6 原流程先按基础候选分选择聪明钱深查币，再生成 V4 排名。这样会出现两类混合展示：观察候选有聪明钱但没有 V4 排名；真正形成 V4 触发的候选可能没有被深查，只能按中性处理。该问题会降低决策可解释性，并让有限的 Binance REST 预算用在非执行候选上。

## 本次变更

1. 第一遍只计算 V4 基础排名、方向、入场结构、保守净期望、同类证据和流动性。
2. 按基础 V4 预排结果选择去重币种短名单，优先已接近准入条件、已进入决策候选和基础排名靠前的币种。
3. 聪明钱深查仍受 `smart_flow_symbol_limit` 限制，默认最多 12 个币种；同币种多空只请求一次，5 分钟缓存和快车道中性回退保持不变。
4. 将聪明钱方向修正加入候选模型后执行第二遍 V4 最终排名。
5. 保存基础预排快照，Dashboard 同时展示预排与最终排名，并明确“未形成 V4 触发”“未进入决策短名单”“等待缓存”和“按中性处理”。
6. 漏斗中的聪明钱覆盖、短名单和修正数量按去重币种统计，避免多空两行重复计数。

## 安全边界

- 聪明钱仍然是最多 `±5` 分的软评分，不是独立开仓条件。
- 数据缺失、置信度不足或接口异常都按中性处理，不绕过 V4 硬门、最小下单量、流动性门槛、交易所保护单或 5U 硬停止。
- V4.6.1 使用独立策略版本和许可证证据；旧版本不参与当前准入、信用和仓位。

## 性能与 API

- 预排和最终重排复用第一遍加载的同类证据和局部熔断上下文，避免重复数据库读取。
- 只对 V4 预排短名单使用聪明钱 REST 预算；快车道不额外集中请求。
- 预计新增开销主要是内存中的一次模型重算，不改变扫描币种池和 Binance REST 预算上限。

## 验收标准

- V4 候选能区分基础预排和最终排名。
- 观察候选不再伪装成可执行 V4 候选。
- 同币种多空只消耗一次聪明钱查询预算。
- 聪明钱不可用时明确显示中性原因，不阻断候选。
- 关闭聪明钱后，基础 V4 结果保持原有行为。
- 后端测试、前端构建、静态资源冒烟和部署后持仓保护检查全部通过。
